## 二、API设计

### POST /api/interpret

事件解读，返回判决卡（SSE流式）。

```
Request:
{
  "event": "今天上班迟到了，被领导当众批评",
  "framework": null          // null=随机, 或指定框架id
}

Response (SSE stream):
data: {"type": "framework", "id": "cthulhu", "name": "克苏鲁世界观"}
data: {"type": "content", "text": "经考证，"}
data: {"type": "content", "text": ""迟到"这一现象..."}
...
data: {"type": "done", "verdict_id": "uuid"}
```

### POST /api/worldview/expand

展开完整世界观（SSE流式）。

```
Request:
{
  "event": "今天上班迟到了，被领导当众批评",
  "framework": "cthulhu"
}

Response (SSE stream):
data: {"type": "section", "title": "核心隐喻", "content": "..."}
data: {"type": "section", "title": "天意本质", "content": "..."}
...（六段）
data: {"type": "done"}
```

### POST /api/worldview/custom

自定义世界观生成（SSE流式）。

```
Request:
{
  "concept": "赛博朋克",
  "event": "可选，关联事件"
}

Response (SSE stream):
data: {"type": "section", "title": "核心隐喻", "content": "..."}
...（六段）
data: {"type": "done"}
```

### GET /api/frameworks

获取所有可用框架列表（用于前端展示）。

```
Response:
{
  "frameworks": [
    {"id": "cthulhu", "name": "克苏鲁", "tagline": "一切皆是旧日支配者的梦境"},
    ...
  ]
}
```

## 三、Prompt工程策略

### 判决卡 Prompt 结构

```
[System]
你是"新三国机制解读局"的首席解读官。你的职责是用{framework_name}世界观的规则，
对用户描述的现实事件进行严肃、学术性的解读。

规则：
1. 语气：学术论文/官方判决书。绝对严肃，零反讽，零自嘲。你完全相信自己说的话。
2. 结构：事件定性 → 机制引用（1-3条）→ 最终判决
3. 字数：150-300字
4. 必须引用具体机制名称（如"星夜加成""骄兵必败循环"）
5. 禁止：网络用语、emoji、"哈哈"、打破第四面墙

[机制库（动态注入相关机制）]
{relevant_mechanisms}

[世界观框架描述]
{framework_description}

[Few-shot示例]
{example_verdict}

[User]
事件：{user_event}
请出具判决书。
```

### 世界观展开 Prompt 结构

```
[System]
你是新三国平行世界研究院的资深学者。请基于{framework_name}世界观，
对以下事件背后的世界运行逻辑进行完整的学术论述。

严格按以下六段结构输出，每段200-400字：
一、核心隐喻
二、天意本质
三、机制解释（选取3-5条机制）
四、角色定位
五、名场面重释
六、自洽性论证

[机制库（完整）]
{all_mechanisms}

[世界观框架描述]
{framework_description}

[参考：已有世界观示例（few-shot）]
{example_worldview_excerpt}

[User]
触发事件：{user_event}
请展开完整世界观论述。
```

### 自定义世界观 Prompt 结构

```
[System]
你是新三国平行世界研究院的开创性学者。用户提出了一个全新的世界观假说。
请基于新三国的底层机制库，构建一个完整、自洽的新世界观体系。

要求：
1. 将用户概念与新三国机制深度融合（不是简单贴皮）
2. 严格六段结构
3. 机制引用必须来自机制库，不可自创
4. 自洽性论证必须逻辑闭环

[机制库（完整）]
{all_mechanisms}

[参考：已有世界观的构建方式（few-shot）]
{two_example_frameworks}

[User]
新世界观假说：{user_concept}
（可选关联事件：{user_event}）
请构建完整世界观。
```

### 机制选取策略

判决卡不需要注入全部机制（太长），由 `prompt_builder.py` 根据事件关键词 + 框架特征选取3-8条相关机制注入。世界观展开和自定义则注入完整机制库。

### Phase 6：名场面目标机制

> 依赖顺序：先 world_clock 时间模型 + registry 新字段 → 再准备期行动盘接入 → 后就位判定与超时失败 + 服务端存档 → 最后章首时间轴揭示 UI。

- [ ] **world_clock 时间模型**：`state` 顶层新增 `world_clock = {chapter, current_season, turns_left}`，每章一条时间轴（如 189 年春夏秋冬），名场面锚定时节，由 director/时间节点推进；玩家准备期行动消耗世界时间，时钟推进
- [ ] **registry 场景新字段**：`fame_moment`（是否关键名场面）、`fame_season`（锚定时节）、`entry_conditions`（就位条件列表，如「在曹操身边」）、`prep_actions`（准备期行动盘：`{text, cost_turns, grants[就位条件], effect}`）
- [ ] **准备期行动盘接入 narrate-options**：名场面之间玩家从 `prep_actions` 选准备行动（投靠/乔装/买情报/赶路），行动消耗时间 + 积累就位条件 `qualifications`
- [ ] **就位判定与超时失败**：`scene_state` 增加 `qualifications`（list[str] 已积累就位条件）；名场面时节到时 `entry_conditions ⊆ qualifications` 则触发名场面（走现有场景叙事），不满足则错过关键名场面 → 游戏失败；普通场景错过不失败
- [ ] **服务端存档**：关键名场面开始前自动存档，失败读档回上个名场面重打（worlds.db 服务端持久化，GameState 序列化 `to_dict`）
- [ ] **章首时间轴揭示 UI**：章首揭示本章时间轴 + 名场面链（时节/就位条件/剩余时间），目标全可见，玩家明确要赶什么
- 验收：核心循环跑通——章首揭示 → 准备期行动盘自由行动（消耗时间+积累就位条件）→ 世界时钟推进 → 名场面时节到：就位条件满足→触发名场面 / 不满足→错过关键名场面→失败；失败可读档回上个名场面重打

## 七、启动方式

### 7.1 本地开发（Windows）

```bat
start.bat    # 一键启动后端 + 前端
stop.bat     # 一键停止
```

| 脚本 | 行为 |
|------|------|
| `start.bat` | 新窗口运行 `backend\python main.py`（uvicorn :8000，`reload=True`）+ `frontend\npm run dev`（vite :5173） |
| `stop.bat` | 后端：PowerShell 按命令行匹配杀 uvicorn **reloader 父进程 + worker**（因 reload 模式 reloader 会复活被杀的 worker，必须按命令行一次杀干净）；前端：杀 5173 监听进程 |

**端口链**：浏览器 → `http://localhost:5173` → vite 代理 `/api` → `http://localhost:8000`。

**手动启动**（等价 start.bat）：
```bat
cd backend   & python main.py      # :8000
cd frontend  & npm run dev         # :5173
```

### 7.2 Docker 部署（生产）

```bash
docker compose up --build -d       # 构建并启动（含 healthcheck）
docker compose logs -f             # 看日志
docker compose ps                  # 看健康状态（healthy / starting）
docker compose down                # 停止
```

- **多阶段构建**：前端在镜像内编译，无需本地 `npm run build`。
- **healthcheck**：每 30s 用 python urllib 打 `http://127.0.0.1:80/api/health`，3 次失败标记 unhealthy。
- **`.dockerignore`**：`.env`、`*.db`、`rag_index.pkl` 等不进入镜像；密钥只经 `env_file: ./backend/.env` 运行时注入。
- **entrypoint.sh**：`set -e` + `nginx`（daemon）→ `exec uvicorn main:app :8000`（成为 PID 1，优雅停机）。

### 7.3 环境变量

| 变量 | 必填 | 说明 |
|------|------|------|
| `DEEPSEEK_API_KEY` | ✅ | 主 LLM |
| `HY3_API_KEY` / `HY3_BASE_URL` / `HY3_MODEL` | 备 | 兜底 LLM |
| `ARK_API_KEY` | 需氛围图时 | 火山引擎图像生成（`scripts/generate_atmo.py` 用，**勿提交**） |
| `CORS_ORIGINS` | 生产 | 逗号分隔白名单，默认 `http://localhost:5173` |
| `RATE_LIMIT` / `RATE_WINDOW` | 生产 | 每 IP 限流（默认 30 次/60s） |

## 八、风险与应对

| 风险 | 应对 |
|------|------|
| DeepSeek API不稳定/限流 | Hy3 TokenHub自动fallback |
| LLM输出不符合格式要求 | Prompt中严格约束 + 后端解析容错 |
| 生成质量不稳定 | Few-shot示例精心打磨，机制库描述精确 |
| 服务器被攻击/滥用 | 简单限流（IP 10次/分钟），无登录但够用 |
| 比赛截止前未完成 | Phase 1-2是核心，Phase 3-5可压缩 |
| 知识库JSON转化工作量大 | 用脚本半自动转化，AI辅助结构化 |
